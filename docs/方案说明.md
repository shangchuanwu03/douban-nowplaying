# 方案说明：豆瓣正在听

这份文档记录「实时按收听专辑打分」这件事是怎么拆解、怎么选型、怎么落地的，以及踩过的坑。

---

## 一、需求拆解

需求一句话是「接入豆瓣，按我收听的专辑实时打分」。它其实包含三个可以独立成立的能力，强度依次递增：

| # | 能力 | 难点 |
| --- | --- | --- |
| 1 | **知道你在听哪张专辑** | Windows 没有公开的「全局正在播放」API 给普通程序用 |
| 2 | **把这张专辑对上豆瓣条目** | 豆瓣早就关了公开 API，只能从网页拿数据；且同一个专辑有多个版本 |
| 3 | **把你的评分写回豆瓣** | 需要登录态，且要处理 CSRF 令牌 |

对应的三个不可靠假设（也是后来真实踩到的）：

- 假设播放器会乖乖上报信息 → 有的会（Apple Music / Spotify），有的不会
- 假设豆瓣能稳定抓 → 连续请求十几次就会被降级成空壳页
- 假设网页结构不变 → 搜索页曾经是 `j/subject_suggest` 接口，现在返回空数组了

产品形态定为**桌面悬浮窗**：常驻右下角、置顶、圆角轻卡片，切歌时自己更新，不抢焦点。

## 二、关键决策

### 1. 怎么拿到「正在播放」

三条路：

| 方案 | 覆盖 | 代价 |
| --- | --- | --- |
| 各播放器自己的 API（Apple Music 无公开接口） | 差 | 每家都要单独适配，还得逆向 |
| Last.fm scrobble | 中 | 延迟 1–5 分钟，不是「实时」，且要先装 scrobbler |
| **Windows 系统媒体控制（SMTC）** | 好 | Win10 1809+ 才有，个别播放器不上报 |

选 SMTC。它由系统统一汇总，Apple Music 桌面版、Spotify、网易云、QQ 音乐、foobar2000 都会往这里报，一次适配全部覆盖。

实测拿到的数据：

```json
{"app":"AppleInc.AppleMusicWin_nzyj5cx40ttqa!App","status":"Playing",
 "title":"叶惠美","artist":"周杰伦","album":"叶惠美",
 "position":12.4,"duration":242}
```

**坑**：SMTC 也会把浏览器里播放的视频报上来。所以加了一层会话过滤 —— 标题命中「哔哩哔哩 / YouTube / Netflix」等直接忽略；浏览器来源还要求带专辑或艺人信息、或标题里出现音乐站点名，才认为是听歌。

### 2. 为什么不用 Electron

第一版就是 Electron：透明无边框窗口、`alwaysOnTop`、托盘、全局快捷键，代码都写完了（`main.js` / `preload.js` / 三套窗口）。结果在这台机器上 **Electron 一启动就崩**：

```
exit=-1073741819  (0xC0000005 ACCESS_VIOLATION)
```

排查过程：换 Electron 32 同样崩；`--no-sandbox`、`--disable-gpu`、`--single-process`、项目内 `--user-data-dir` 全部无效；用计划任务在用户会话里启动仍然崩。但同一台机器上：

- 手写编译的 WinForms exe 正常弹窗、正常跑消息循环
- WPF 正常
- Edge 无头模式正常渲染

结论：不是权限、不是沙箱、不是没有桌面，是 Chromium 内核在这台机器上起不来。**于是改用 .NET Framework 自带的 WPF。**

| | Electron | WPF（最终） |
| --- | --- | --- |
| 体积 | ~370 MB | **53 KB**（依赖系统 .NET 4.x） |
| 启动 | 1–2 s | ~200 ms |
| 圆角与投影 | 支持 | 支持（`AllowsTransparency` + `DropShadowEffect`） |
| 开发效率 | 高（HTML/CSS） | 中（XAML） |
| 本机可用性 | ❌ 崩溃 | ✅ 已验证 |

代价是界面要用 XAML 重写一遍。但换来的是「真的能跑」。网页版界面没有浪费 —— 管理页（收听史 / 手动绑定 / 设置）仍然是网页，用浏览器打开。

### 3. 怎么从豆瓣拿数据

豆瓣没有公开 API（`api.douban.com/v2` 早已下线），只能解析网页。三条链路都实测过：

| 用途 | 地址 | 拿到的内容 |
| --- | --- | --- |
| 搜索（主） | `music.douban.com/subject_search?search_text=` | 页面内嵌 `window.__DATA__` JSON：id、标题、艺人、评分、评价数 |
| 搜索（备） | `www.douban.com/search?cat=1003` | 服务端渲染 HTML，字段略少但不会被降级 |
| 详情 | `music.douban.com/subject/{id}/` | 评分分布、出版者、介质、发行时间、条形码、简介、标签、短评 |
| 回写 | `POST music.douban.com/j/subject/{id}/interest` | 需要 Cookie + `ck` 令牌 |

**坑一：限流**。连续请求 10 多次后，搜索页会从 SSR 变成 JS 空壳（`正在搜索...`，没有 `__DATA__`）。对策在后面「稳定性设计」里。

**坑二：结构不统一**。详情页 `#info` 区块里，「表演者」是 `<span><span class="pl">表演者: <a>周杰伦</a></span></span>`，而「流派」是 `<span class="pl">流派:</span> 流行`。用正则逐字段抓必然串行（介质抓成了 `CD 发行时间:`）。改成**先转纯文本、按 `<br>` 切行、再按「标签: 值」解析**，立刻稳定。

**坑三：Cookie**。不带 `bid` 时，豆瓣把每个请求都当新访客，更容易被降级。所以做了持久 Cookie jar，首次访问先领 `bid` 存到 `data/http-cookies.json`。

## 三、系统结构

```
┌─────────────────────────────────────────────────────────────┐
│  douban-overlay.exe  (C# / WPF)                             │
│  浮窗：置顶 · 圆角卡片 · 900ms 轮询 /api/state              │
│  管理窗：收听史 / 手动绑定 / 设置（同进程，不跳浏览器）      │
└───────────────▲─────────────────────────────┬───────────────┘
                │ HTTP + SSE                  │ 点击星星/同步
┌───────────────┴─────────────────────────────▼───────────────┐
│  node server (127.0.0.1:4590)                                │
│  状态机 · 会话过滤 · 匹配调度 · 缓存 · 评分持久化            │
└───────▲──────────────────────────────┬──────────────────────┘
        │ stdout JSON 行               │ HTTPS
┌───────┴──────────────┐      ┌────────▼─────────────────────┐
│ powershell smtc.ps1  │      │ music.douban.com             │
│ 常驻进程，900ms 轮询  │      │ 搜索 / 详情 / 回写            │
│ Windows SMTC         │      └──────────────────────────────┘
└──────────────────────┘
```

三个进程各司其职：

- `smtc.ps1` 常驻（不是每次调用起一个新 PowerShell，那要 300ms 启动开销），只在**状态变化**时往 stdout 打一行 JSON
- Node 服务做「去抖 + 匹配 + 缓存」，浮窗只管显示
- 浮窗不直接碰豆瓣，换前端（网页/CLI/手机）都不用改数据层

## 四、匹配算法

拿到 `{album, artist, track}` 后搜豆瓣，对每条候选打分。排序原则是 **艺人优先、标题次之**：

```
score = 艺人相似度 × 62        ←  主信号：这是谁
      + 标题相似度 × 30        ←  次信号：是哪一张
      + 同名加成（标题完全一致 +6）
      + 评分人数（min(1, log10(评价数)/5.5) × 12）
      + 类型加成（专辑 +8 / EP +2 / 单曲 −4 / 现场 −8）
```

评分人数从 6 分提到 12 分，并加了「同名 +6」：一张专辑常有首发版、再版、引进版、黑胶版，标题一样、艺人也一样，这时**评分人数多的那个才是主版本**。同名又压过「标题长得像但票更多」的条目，避免被合辑/演唱会版抢走。

实测排序（构造数据，同一艺人）：

| 候选 | 分数 |
| --- | --- |
| 同名 · 119449 人 | 117.1 |
| 同名 · 3789 人 | 113.8 |
| 同名 · 88 人 | 110.3 |
| 近似标题（「叶惠美 演唱会」）· 5 万人 | 106.1 |
| 别的歌手 · 同名 · 9.9 万人 | 54.9（被艺人门槛直接拒掉） |

为什么不是标题优先：豆瓣上同名专辑太多 ——「Greatest Hits」「精选」「Home」这类标题，
标题分再高也分不出是谁的。反过来，艺人对不上时，标题越像越危险。

几条设计取舍：

- **标题先做清洗**：播放器常在专辑名后塞形态后缀（Apple Music 把 EP 报成 `I've IVE - EP`），
  而豆瓣搜索会把 `- EP` 当检索词，导致真正的专辑根本不在返回列表里 —— 这是「明明有却找不到」
  的首要原因。查询和比对前统一剥掉 `- EP / - Single / (Deluxe Edition) / (Remastered)` 这类尾巴。
- **候选缺艺人信息时**（豆瓣个别条目没写表演者），把 92 分权重整体让给标题。
  「缺数据」不该被当成「不相关」。
- **艺人相似度**同时看整串和分词：整串相等 = 1；一方包含另一方 = 0.8~1.0（`周杰伦` 对 `周杰伦 Jay Chou`）；
  分词命中再补一刀，但会跳过 `the / and / feat` 这类虚词，避免 `The Beatles` 命中 `The Kinks`。
- **三条硬规则**（宁可让你手动绑定一次，也不悄悄指错）：
  - 两边都有艺人却对不上（< 0.35）→ 丢弃
  - 标题完全不像（< 0.45）→ 丢弃，否则会随手挑一张这位歌手的热门专辑
  - 总分 ≥ 78 且（标题 ≥ 0.5 或艺人 ≥ 0.95）才写入 30 天缓存
- 详情缓存 7 天（评分会变），并带 `CACHE_VERSION`，解析逻辑一改旧缓存自动失效

检索顺序也按艺人优先：`艺人 + 专辑名` → `艺人 + 歌名` → `专辑名` → `歌名`，
最多查 3 次；一旦「艺人 ≥0.9 且标题 ≥0.65」就提前收工。

实测效果（置信度即上式总分，满分约 106）：

| 输入 | 命中 | 置信度（艺人/标题） |
| --- | --- | --- |
| 叶惠美 / 周杰伦 | 叶惠美（9.3 分，11.9 万人） | 92（1 / 1） |
| 范特西 / 周杰伦 | 范特西（9.5 分，19.2 万人） | 92（1 / 1） |
| OK Computer / Radiohead | OK Computer（9.4 分，5.2 万人） | 92（1 / 1） |
| Abbey Road / The Beatles | Abbey Road（9.6 分，3.1 万人） | 92（1 / 1） |
| 叶惠美 / **蔡依林** | 无匹配（拒绝跨歌手） | — |
| Abbey Road / **The Kinks** | 无匹配（虚词不参与命中） | — |

## 五、界面设计语言：新拟物派

界面按「元素与背景同色，只用两段阴影说明凹凸」来做，不用边框、不用实色分区、不叠深色玻璃。

```
base      #e0e5ec   页面与所有元素的共同底色
shadow    #b8bcc2   右下冷灰阴影
highlight #ffffff   左上白色高光
ink       #3d4451   内容文字
blurple   #6d5dfc   唯一强调色：主按钮、选中态
mint      #4ecdc4   正向反馈（已同步、正在播放）
coral     #ff6b6b   错误
```

落地的几条规矩：

- **凸起**（卡片、封面、按钮）：`8px 8px 16px #b8bcc2` + `-8px -8px 16px #ffffff`
- **凹陷**（输入框、进度槽、分段轨道）：同一对阴影翻成 inset
- **hover 时模糊减半**，模拟手靠近遮光（按钮跟着变软）
- 卡片圆角 24，按钮/输入 16，卡片内边距 24，元素间距 16
- 字重不超过 600，字号 12/14/16/20/34，紫罗兰面积只出现在按钮与选中态

**一个必须说明的取舍**：新拟物要求「不能换底色」，所以悬浮窗从原来的半透明深色玻璃改成了**不透明浅色卡片** —— 半透明会让阴影计算失去参照，材质感立刻垮掉。浮窗与桌面的分离改由外层投影承担。

**为什么设置窗口不跳浏览器**：Windows 的前台窗口规则下，新开的浏览器标签经常抢不到焦点。实测默认浏览器（ego-lite）会把管理页留在 Apple Music 窗口后面，用户只看到音乐播放器，自然以为「设置没出来」。改成同进程的 WPF 窗口后，置前是确定的，也顺带不再依赖用户装了哪个浏览器。

WPF 只能给一个元素挂一个 `DropShadowEffect`，双阴影是靠**两层同色 Border 叠在一起**（一层向下右投影、一层向上左投影），再由最上层的实心卡片盖住中间部分实现的；凹陷则用同色系的对角渐变模拟 inset。网页端（管理页）直接用 CSS 的 `box-shadow` 双值，与设计稿一一对应。

## 六、两套皮肤

界面可以在两套设计语言之间切换，选择存在 `data/db.json` 的 `settings.skin`，启动时恢复。

| | 新拟物（默认） | 玻璃拟态 |
| --- | --- | --- |
| 底色 | `#e0e5ec` 浅灰 | `#0b1322` 夜墨 + 两团柔光斑 |
| 面板 | 同色 + 双外阴影 | 8% 白 + 1px 白 15% 描边 |
| 层次 | 阴影承担 | 明度与模糊承担 |
| 强调色 | 紫罗兰 `#6d5dfc` | 香槟金 `#e4b863` |
| 关键数字 | 墨色 | 香槟金 |
| 圆角 | 卡片 24 / 控件 16 | 卡片 24 / 控件 14 / 按钮全圆 |

**实现方式**：每套皮肤是一个独立的 XAML（`overlay.xaml` / `overlay-glass.xaml`，`settings.xaml` / `settings-glass.xaml`），但元素名完全一致，所以同一份 C# 逻辑直接复用。切换时重设调色板槽位 → 销毁并重建窗口（保持位置）→ 重新绑定元素。为此把 `ShutdownMode` 改成了 `OnExplicitShutdown`，否则关掉主窗口会直接退出进程。

**WPF 的硬限制**：`backdrop-filter: blur(40px)` 没有对应物——WPF 无法模糊窗口背后的桌面。所以玻璃皮肤的「可模糊的背景」是自绘的：卡片内部铺夜景底 + 两团大半径径向光斑（`RadialGradientBrush`），面板再用 8% 白叠上去。视觉上成立，但它借的是自己的光，不是桌面壁纸的光。真正的背景模糊要换 WinUI 3 的 `DesktopAcrylicBackdrop` 或 WebView2，那是另一个量级的改动。

## 七、登录与账号绑定

目标：不要求用户去翻 DevTools、不要求手抄一长串 Cookie。最终方案是 **默认浏览器登录 + 剪贴板一键导入**。

流程：

1. 设置页「打开豆瓣」→ 用系统默认浏览器打开 `www.douban.com`
2. 用户在熟悉的浏览器里登录（有插件、有密码管理器、有已登录的会话）
3. 全选复制 Cookie → 回到设置页点「从剪贴板读取」
4. 程序用正则捞出 `bid` 与 `dbcl2`，拼成 Cookie 头
5. 服务端验证：从 `dbcl2` 的 UID 访问 `/people/{uid}/` 取昵称，跳登录页即过期
6. 验证通过才写入 `settings.doubanCookie` + `settings.doubanUser`，界面显示「已绑定：昵称」

### 为什么不是全自动抓取

先尝试过「自行拉起受控浏览器 + DevTools 协议读 Cookie」：启动 Edge（临时 profile、`--remote-debugging-port`）、连 CDP、`Storage.getCookies`。链路本身能跑通（确实读到了豆瓣下发的 `bid`），但在这台机器上遇到了两个没法稳定绕开的问题：

- 命令行 URL 与 `Page.navigate` 都会停在 `about:blank`，必须用 `Target.createTarget` 才能在浏览器层开出带地址的页面；
- 页面能加载（Cookie 有下发）却整页空白，怀疑是该会话下 Edge 的 GPU 进程异常。

而「读默认浏览器的 Cookie 数据库」这条路是死的：新版 Chrome/Edge 用 App-Bound 加密，密钥绑在浏览器进程上，外部解不开；硬解既有法律风险也不可靠。所以放弃自动抓取，改成「默认浏览器 + 剪贴板」，把不可控的环节交还给用户熟悉的浏览器。

### 导入「我听过的音乐」

绑定之后可以把已有评分拉进本地，目的是**避免误覆盖**：豆瓣同一张专辑只有一条评分记录，重复提交不会产生两条，但会用新值覆盖旧值。不知道你原来打了几分就点「同步」，是有风险的动作。

实现：

- 抓 `music.douban.com/people/{uid}/collect?start=N&type=music`（15 条/页），解析条目 id、标题、表演者、星级（`ratingN-t`）、打分日期、短评
- 分批拉取，游标存进 `settings.importCursor`，中断后从断点继续；拉完自动归零
- 两种入口跑的是同一套接口：应用内按钮会一直循环到拉完；命令行版 `scripts/import-collection.js`（双击 `导入豆瓣收藏.bat`）逐批打印进度，适合收藏特别多的时候挂后台
- 导入的评分标记 `source: douban` + `synced: true`，浮窗上直接显示为「已同步」，按钮不再提示同步

一个解析坑：短评和打分日期在相邻的两个 `<li>` 里，早期正则把日期一起吞进了评论（如「2026-11-22 自由颂太有灵气了」），已修并在数据里清理。

### 剪贴板解析

DevTools 里复制出来的内容形态不固定（整段 Cookie、只有两行、带引号、带空格），解析器按 `bid=` / `dbcl2=` 做正则提取，并对 `dbcl2` 自动补回引号（豆瓣下发的原值本身带引号，去掉容易校验失败）。

## 八、稳定性设计




豆瓣是「能抓但别抓太狠」的状态，所以：

1. **限速**：全局最小间隔 1.8 s，所有请求共用一个队列
2. **持久会话**：`bid` 存盘复用，被当成同一访客
3. **双数据源**：主搜索拿不到 `__DATA__` 就等 4 s 重试一次，仍失败自动切老版搜索
4. **三级缓存**：匹配结果 30 天 / 详情 7 天 / 封面落盘永久
5. **去抖**：切歌后等 1.1 s 才发请求，连续切歌不会打出一串无用请求
6. **历史门槛**：连续播放 20 s 才记一条，跳过「下一首下一首」的试听

## 九、评分回写

```
POST https://music.douban.com/j/subject/{id}/interest
Cookie: bid=…; dbcl2=…
Body:   ck=<页面令牌>&interest=do&rating=5&comment=…&status=done
```

`ck` 令牌藏在登录后的「收藏」链接里（`…?reason=collectdo&ck=xxxx`），所以每次回写前先拉一次详情页取令牌。未登录时该链接的 `ck=` 是空的 —— 正好用来判断登录态是否失效。

不配置 Cookie 时整个写回按钮是禁用状态，只读浏览不受影响。

## 十、已知风险

| 风险 | 影响 | 现状 |
| --- | --- | --- |
| 豆瓣改版 | 解析失效 | 有备用源；解析集中在 `parseSubjectPage`，改一处即可 |
| 豆瓣封 IP | 长时间不可用 | 限速 + 缓存；极端情况需换网络 |
| Apple Music 不报专辑名 | 只能按歌名匹配，容易落到单曲 | 按歌名兜底 + 手动绑定 |
| `dbcl2` 过期 | 写回失败 | 提示重新粘贴 Cookie |
| 同专辑多版本 | 匹配到再版/引进版 | 手动绑定一次即永久生效 |

## 十一、路线图

**v1（已完成）**
- SMTC 实时识别 + 会话过滤
- 豆瓣搜索/详情解析 + 双源降级 + 缓存
- 悬浮窗（置顶/圆角/进度条/我的评分/短评/同步）
- 收听史、手动绑定、Cookie 设置页

**v1.1（打磨）**
- 托盘图标 + 开机自启
- 浮窗位置记忆、贴边自动收窄
- 主题（浅色 / 跟随壁纸）
- 识别「专辑里换歌」时不闪

- 月度收听报告：高分专辑、流派分布、与豆瓣均分的差

- AI 生成短评草稿（可选，接你自己的模型 API）

**v3（多端）**
- 手机端：把手机播放的专辑投到电脑浮窗
- 非 Windows：以 Last.fm scrobble 作为数据源，浮窗换成 Tauri / 原生
